# BookSwap — Security Review

This is a structured check of the BookSwap API against the most common ways APIs get breached. It follows the **OWASP API Security Top 10**, the industry's standard list of API risks. Each of the seven categories below asks one question, records what we found, rates the impact, and names a fix with an owner.

The code does not change today, so some findings are "verify this in the code" rather than confirmed bugs. Those are marked accordingly.

### Key terms (used throughout)

- **Authn (Authentication)** — proving *who you are* (logging in).
- **Authz (Authorization)** — what you are *allowed to see or do* once logged in.
- **BOLA (Broken Object Level Authorization)** — the #1 API risk: the API trusts an ID in the URL without checking that you own that object.
- **JWT (JSON Web Token)** — the signed token that proves a member is logged in.
- **PII (Personally Identifiable Information)** — data that identifies a person: name, email, address.
- **TLS (Transport Layer Security)** — the encryption behind HTTPS.
- **WAF (Web Application Firewall)** — Azure Front Door's filter that blocks bad traffic and enforces rate limits.
- **CWE (Common Weakness Enumeration)** — a standard ID for a *type* of weakness (e.g. CWE-89 = SQL injection).
- **CORS (Cross-Origin Resource Sharing)** — browser rules for which websites may call the API.

### How severities are decided

Not everything is "High" — that would be useless. The rule used here:

- **High** — a real privacy breach or account takeover is possible.
- **Medium** — exploitable, but limited in scope or needs certain conditions.
- **Low** — hardening and information leaks; worth fixing, not an emergency.

Result for threats: **2 High, 6 Medium, 2 Low.**

## 1. Review summary (the seven required categories)

| Category | Question | Finding | Severity | Mitigation |
|---|---|---|---|---|
| **Authn** | Is every non-public endpoint protected by JWT? | All endpoints except `/health` require a valid JWT via Entra External ID — good. But `/health` returns SQL/Redis up-down status **without login**, which leaks internal state. | Low | Public `/health` returns `{status:"ok"}` only; keep detailed readiness behind auth or an internal network. |
| **Authz** | Does every `/{id}` endpoint check object ownership? | **No.** `GET /members/{memberId}/loans` and `GET /members/{memberId}` appear to check "valid JWT" but **not** "does this token belong to `{memberId}`". Any logged-in member can read another member's loans and address. **(BOLA — see F1)** | **High** | Derive `memberId` from the token, not the URL (prefer `GET /me/loans`); otherwise enforce `token.sub == memberId` else `403`. Add an automated authorization test. |
| **Injection** | Are all database queries parameterised? | Writes use parameterised queries. **Verify** the search filter `GET /books?q=...` is not building SQL by string concatenation — that is the classic injection spot. | Medium | Parameterised queries everywhere; for any dynamic sort/filter, allow-list the column names. |
| **Secrets** | Where are connection strings stored? | Design mandates Key Vault (good). **Verify** no `.env` or connection string was ever committed to the repo, and that App Service uses Key Vault references + Managed Identity, not plaintext App Settings. | Medium | Key Vault references + system-assigned Managed Identity; add secret scanning (gitleaks) to CI; rotate anything ever exposed. |
| **Transport** | Is TLS enforced at Front Door? | Front Door enforces HTTPS. But the App Service **origin** may still accept direct HTTP, letting an attacker bypass the WAF and rate limits entirely. | Medium | App Service "HTTPS Only" = on; restrict inbound to the Front Door service tag; verify the `X-Azure-FDID` header; TLS 1.2 minimum. |
| **Rate limit** | Are auth and write endpoints rate-limited? | Write endpoints are rate-limited at Front Door (good). But **read** endpoints that expose PII — `GET /members/{memberId}` — are **not**, which allows ID enumeration and mass scraping. **(see F3)** | Medium | Add a Front Door rate rule (e.g. 60/min per IP) on member reads and any email-triggering endpoint; add per-account caps. |
| **PII** | What PII appears in responses, logs, or queues? | Responses correctly return address only to the owner (once BOLA is fixed). **Risk:** if the app logs full request bodies or query strings, emails/addresses land in Application Insights telemetry for 90 days. **(see F2)** | High | Strip PII before logging; never log bodies or `Authorization` headers; log `memberId` not name/email; send `memberId` (not email) in Service Bus messages. |

## 2. Detailed findings

### F1 — BOLA on member endpoints  ·  Severity: High  ·  OWASP API1:2023, CWE-639

**The problem:** the endpoints trust the ID in the URL. A valid login is checked, but not *ownership*.

**Concrete attack (the required URL + request):**

```http
# Attacker is logged in as member A (token subject = a1111-1111-1111),
# using their OWN valid token. They simply change the ID in the URL to member B.

GET /members/b2222-2222-2222/loans HTTP/1.1
Host: api.bookswap.example
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...   # member A's valid JWT

# Vulnerable response:  200 OK  + member B's full loan history
# Safe response:        403 Forbidden
```

The same trick on `GET /members/b2222-2222-2222` returns member B's **home address** — a direct breach of requirement N7.

**Fix (implementable):**
- Best: remove the ID from the URL and read the member from the token — `GET /me/loans`. The user cannot ask for data that isn't theirs.
- Otherwise, guard every handler:
  ```js
  if (req.auth.sub !== req.params.memberId && !req.auth.roles.includes('admin')) {
    return res.status(403).json({ error: 'forbidden' });
  }
  ```
- Add an automated test: "member A requests member B's resource → expect 403."

### F2 — PII leak through logs / telemetry  ·  Severity: High  ·  CWE-532

**The problem:** the audit requirement (N9) is good — it logs `requestId` + `memberId`. The danger is *over*-logging. If a global request logger or the Application Insights SDK captures full request bodies, query strings, or the `Authorization` header, then emails, addresses, and tokens sit in the `traces` table for the 90-day retention period, queryable by anyone with workspace access.

**Fix (implementable):**
- Use an Application Insights **telemetry initializer** to drop `Authorization` headers and request bodies before send.
- Log a pseudonymous `memberId`, never name / email / address.
- In Service Bus messages, send `memberId` and let the worker look up the email — don't put the email in the queue.
- Write these down as **redaction rules** in the observability plan (Deliverable 4).

### F3 — Missing rate-limit on member reads  ·  Severity: Medium  ·  OWASP API4:2023, CWE-770

**The problem:** `GET /members/{memberId}` has no per-IP limit. An attacker can loop through member IDs and scrape the directory. On its own this is Medium; combined with the F1 BOLA bug it becomes a bulk PII breach.

**Fix:** add a Front Door WAF rate rule — 60 requests / 60 s per IP on member reads — returning `429`. Add a per-account cap so one token can't enumerate either.

### Shorter notes on the remaining categories

- **Authn / `/health` (Low):** returning dependency status unauthenticated helps an attacker time an attack. Return only `{status:"ok"}` publicly.
- **Broken auth / tokens (Medium):** 1-hour expiry is set (good), but there's no revocation on logout — a stolen token stays valid until it expires. Add refresh-token rotation and a deny-list for high-value actions.
- **Injection (Medium):** confirm the search filter is parameterised; allow-list any dynamic column names.
- **Secrets (Medium):** confirm Key Vault + Managed Identity and no committed `.env`; add gitleaks to CI.
- **Transport (Medium):** lock the App Service origin to Front Door so the WAF can't be bypassed.

## 3. OWASP ZAP baseline scan

**What ZAP is:** OWASP ZAP (Zed Attack Proxy) is a free security scanner. The **baseline** scan is *passive* — it crawls the running API and inspects responses for missing security headers and misconfigurations, without attacking. It is a fast first pass, not a full penetration test.

The scan was run against the Prism mock at `http://host.docker.internal:4010`. The report is attached as **`navindu-day3-zap-baseline-report.html`**.

**One finding discussed (as required):**

> **Cross-Domain Misconfiguration — `Access-Control-Allow-Origin: *` (Medium).**
> ZAP flagged that the API returns a wildcard CORS header, meaning *any* website could call the API from a browser. For a member-facing app this is too open — a malicious site could ride a logged-in member's session. **Fix:** set an explicit allow-list of origins (the BookSwap web app only) and never combine a wildcard with credentials.

**A false positive to be honest about:** ZAP also flags "Content Security Policy Header Not Set." A CSP mainly protects HTML pages against script injection; for a pure JSON API it is largely **not applicable**. It's worth calling out precisely because a good reviewer separates real risks from noise — which is exactly what the challenge hint asks for.

## 5. Defence in depth (one-paragraph note)

No single control should be load-bearing. BookSwap layers its defences: Front Door (WAF + TLS + rate limits) at the edge, JWT authentication at the app door, **object-level authorization inside each handler**, parameterised queries at the database, Key Vault for secrets, and PII redaction in the logs. The lesson from F1 is the point of defence in depth — "we have HTTPS and a login" is not security if the authorization check inside the handler is missing. Each layer assumes the one before it might fail.
