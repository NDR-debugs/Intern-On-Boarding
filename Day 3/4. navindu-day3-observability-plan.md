# BookSwap — Observability Plan

Observability is being able to answer "what is happening inside the system?" from the outside. This plan sets up the three pillars — **logs, metrics, and traces** — decides what we alert on, and states exactly what personal data is stripped before anything is written down.

The rule behind every choice here:

> **Alert on metrics. Debug with logs. Root-cause with traces.**
> And: **alert on symptoms (users are hurting), not causes (a machine is busy).**

### Key terms (used throughout)

- **Metric** — a number over time (latency, error rate, queue depth). Cheap; good for *spotting* trouble.
- **Log** — a detailed record of one event. Rich; good for *understanding* trouble.
- **Trace** — one request followed across every service it touches. Good for *pinpointing* trouble.
- **App Insights (Application Insights)** — Azure's tool that collects metrics, logs, and traces.
- **KQL (Kusto Query Language)** — the query language for App Insights.
- **p95 latency** — the value 95% of requests come in under; a fair "typical worst case."
- **Sampling** — keeping only a fraction of high-volume data to control cost (we never sample away errors).
- **Action group** — the Azure object that says *who* an alert notifies (pager, Teams).
- **Severity (Sev)** — how urgent: **Sev1** = page now, **Sev2** = page, **Sev3** = Teams message only.
- **SLO / SLI** — the targets from the SLO map (Deliverable 1).
- **PII (Personally Identifiable Information)** — name, email, address.

## 1. Setup

### Logs — Azure Monitor Logs
- **Schema:** every log is structured JSON with fixed fields: `timestamp, level, event, memberId, requestId, endpoint, statusCode, durationMs`. Structured fields (not free text) make them queryable.
- **Retention:** application traces **90 days**; security/audit events (`auth.failed`, `loan.created`, `loan.returned`) **365 days** in a workspace with restricted access.
- **Redaction rules:** see Section 7 — no request bodies, no headers, no PII, ever.

### Metrics — Application Insights
- **Request metrics:** duration and result code per endpoint (auto-collected).
- **Dependency metrics:** duration and success for SQL and Redis calls (auto-collected).
- **Custom metrics:** `listing.created`, `loan.created`, `loan.returned` counts (emitted by the app).
- Metrics are **low-cardinality** on purpose — grouped by endpoint and status, never by member ID, so they stay cheap.

### Traces — Application Insights distributed tracing
- **Propagation:** the W3C `traceparent` header flows App → SQL → Redis → Service Bus → email worker, so one request is one connected trace.
- **Sample rate:** **100% of errors and all `auth.*` events** are always kept (never sample away a failure or a security event); high-volume *successful* search requests are sampled at **~20%** to control cost.

## 5. What we are deliberately NOT alerting on

Discipline matters as much as coverage. A pager that cries wolf gets ignored. We do **not** page on:

1. **Individual slow requests.** We alert on the SLO *burn rate* over a window. One slow call is noise; a trend is a signal.
2. **CPU or memory on their own.** These are *causes*, not symptoms. High CPU that isn't breaking an SLO is autoscale's job — we page on the user-facing symptom instead.
3. **Cache-miss rate or Redis evictions.** Expected and self-healing. It only matters if it burns the search-latency SLO, which the "Search SLO burn" alert already catches.
4. **A single `5xx`.** We alert on error *rate*, never one error.
5. **Low/informational security-scan findings.** Tracked in `threats.csv` and worked in the backlog — reviewed, not paged.
6. **Normal queue growth below threshold.** The digest queue filling and draining is the design working; only a sustained backlog pages.

## 7. PII and redaction (explicit)

This section closes the F2 finding from the security review. Logging is where PII quietly leaks, so the rules are strict.

**Never logged:** request bodies, query strings containing PII, `Authorization` headers, tokens, member **name**, **email**, or **home address**.

**Logged instead:** a pseudonymous `memberId` (a GUID), `requestId`, `endpoint`, `statusCode`, `durationMs`.

**How it's enforced:**
- An **Application Insights telemetry initializer** strips PII fields before any telemetry is sent, and automatic request-body capture is turned off.
- **Service Bus** messages carry the `memberId`, never the email — the email worker looks the address up only at send time.
- **Metrics stay low-cardinality** (grouped by endpoint/status, never by member), so no PII rides along.
- **Retention & access:** audit logs live 365 days in a restricted workspace; traces 90 days; access is role-limited so a broad "read logs" grant can't become a PII dump.
- **Sampling never drops security signal:** 100% of `auth.*` events and all errors are always kept.
