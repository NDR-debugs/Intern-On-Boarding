# BookSwap — Reliability Runbook v0.1

This runbook explains what happens when three specific things go wrong, and what a human should do about each. For every failure it answers the same five questions: what the member sees, how we detect it, what the design does automatically, what the on-call person does by hand, and what we fix afterwards.

The code does not change today, so anything not yet built is marked as a **follow-up**, not a claim.

### The pattern behind every fix

When a dependency (the database, the cache, a downstream service) misbehaves, the service defends itself in **four layers, in order**:

1. **Timeout** — give up fast. Don't wait 30 seconds for a dead database; give up in 3.
2. **Retry with backoff** — try again 2–3 times, but only for temporary errors, waiting longer between each try.
3. **Circuit breaker** — if it keeps failing, stop calling it for a few seconds so failed calls don't pile up.
4. **Fallback** — still give the member *something*: a cached result, or a queued write for later. Degraded, not broken.

Under all four sits one safety belt for writes: the **idempotency key**, which makes a retried "create" safe so it never produces a duplicate.

### Key terms (used throughout)

- **Timeout** — the longest a call may wait before we give up on it.
- **Retry with backoff** — trying again after a *temporary* failure, waiting longer each time (200 ms, then 400 ms, then 800 ms) so retries don't stampede.
- **Circuit breaker** — a switch that "opens" after too many failures, makes calls fail instantly for a short while, then tests whether the dependency has recovered.
- **Fallback** — the backup plan when the main path fails (serve a stale cache result, or queue the write).
- **Idempotency key** — a unique ID (a **UUID**, Universally Unique Identifier) the client sends with a write, so the server recognises a retry and never creates a second copy.
- **Bulkhead** — reserving part of a resource (e.g. some database connections) so one flood can't drown everything else.
- **RPS (Requests Per Second)** — how busy the service is.
- **SQL** — Azure SQL Database, the source of truth.
- **Redis** — Azure Cache for Redis, the fast cache in front of the database.
- **SLO / SLI** — the reliability targets defined in the SLO map (Service Level Objective / Indicator).
- **HTTP status codes** — `2xx` = success, `202` = accepted (we'll finish it shortly), `4xx` = caller error, `429` = too many requests, `5xx` = server error.

**Paging target (requirement N8):** every detection alert checks **once a minute over a 2-minute window**, so a real outage pages on-call within **~3 minutes**.

## 0. Shared reliability settings

All three failures reuse the same numbers. Keeping them in one place makes them consistent and easy to defend.

### Timeouts — how long we wait before giving up

| Call | Connect | Operation | Why this number |
|---|---|---|---|
| Front Door → app (member-facing max) | — | **30 s** | Hard ceiling; nothing a member sees waits longer. |
| App → SQL | **5 s** | **3 s** | A healthy query is under 100 ms; 3 s means SQL is sick, so stop. |
| App → Redis | **1000 ms** | **250 ms** | The cache is meant to be fast; if it's slow, skip it. |
| App → Service Bus (send) | **5 s** | — | Queuing a message should be quick. |

### Retry policy — temporary errors only

- **Attempts:** 3 (1 original + 2 retries).
- **Backoff:** 200 ms, then 400 ms, then 800 ms, plus a small random 0–100 ms so retries spread out.
- **Retry on:** network errors, `5xx`, and SQL transient error numbers (`40613, 40197, 40501, 49918, 10928, 10929, 4060, 233`).
- **Never retry on:** `4xx` / validation errors — the input is wrong, so retrying just hammers a doomed request.

### Circuit breakers — one per dependency

| Breaker | Opens when | Stays open | Trial calls |
|---|---|---|---|
| **SQL** | ≥ 50% of calls fail over 10 s (min 20 calls) | 30 s | 3 |
| **Redis** | ≥ 20% of calls fail over 5 s (min 20 calls) | 15 s | 3 |

While a breaker is open, calls fail **instantly** into the fallback instead of waiting on the timeout. That is what stops the app freezing.

### Idempotency — the write safety belt

- `Idempotency-Key: <uuid>` header is **required** on `POST /books` and `POST /loans`.
- The server remembers `key → saved response` for **24 hours** (in Redis, backed up in a SQL table).
- A repeated key returns the **original** `201` — it never creates a second row. This is requirement N4.

### Bulkhead and autoscale

- SQL connection pool: **max 20 per instance**, with **5 reserved for writes** so a read flood can't starve `POST /books`.
- App Service autoscale: **min 2 / max 10** instances; **+2 when CPU > 65% for 5 min**; scale back in when CPU < 40% for 10 min.
- Front Door rate limit (WAF = Web Application Firewall): **100 write requests / 60 s per IP address** → `429` with `Retry-After: 30`.

## Failure 1: Azure SQL primary unavailable for 5 minutes

**In one line:** the database is unreachable. Reads fall back to the cache; writes are queued and replayed later, with no duplicates.

### What the member sees
- **Creating a listing** does not error — it returns **`202 Accepted`** ("we've got it, it'll appear shortly"), because the write is queued.
- **Book detail and loan history** that are already cached still load. Uncached ones show a friendly "temporarily unavailable, try again" — never a raw error.
- **Search** keeps working for anything the cache already holds.

### Detection
Primary signal: the SQL dependency failure rate in Application Insights.

```kusto
dependencies
| where timestamp > ago(5m)
| where type == "SQL"
| summarize failRate = round(100.0*countif(success==false)/count(),1) by bin(timestamp,1m)
// Alert: failRate > 25% for 2 minutes
```

Confirming signal: Azure SQL's `connection_failed` metric rising, and the app's readiness probe (a lightweight `SELECT 1`) failing.

### Mitigation in design
- **Timeout:** connect 5 s, command 3 s — threads don't hang for the whole 5-minute outage.
- **Retry:** 3 tries at 200 / 400 / 800 ms, temporary SQL errors only — this bridges a short automatic failover.
- **Circuit breaker (SQL):** opens after repeated failures, so we stop waiting on timeouts and fail fast into the fallback.
- **Fallback:**
  - *Reads* → serve from Redis (stale but useful).
  - *Writes* → publish to **Service Bus** carrying the **idempotency key**, return `202`. A background worker commits to SQL once it recovers, and the key **de-duplicates**, so a queued write plus a client retry still equals one listing.
- **Platform:** SQL uses an **auto-failover group with zone redundancy**; the retry window is sized to cover the ~30–60 s automatic failover.

### Manual response
- **Who is paged:** the BookSwap pod **primary on-call engineer** (Sev2), via Azure Monitor → pager + Teams. Unacknowledged after 10 min → **secondary on-call**, then **pod tech lead**.
- **Steps:**
  1. Open **SQL resource health** and the failover-group state in the portal.
  2. Check whether **auto-failover** finished. If stuck past 2 min, **start a manual failover**.
  3. Confirm the SQL breaker is **open** and writes are **queuing** in Service Bus — this proves the fallback is working, not that data is lost.
  4. When SQL is healthy, confirm the breaker **closes** and the worker **drains** the queued writes.
  5. Run the duplicate-check query to confirm the idempotency keys prevented any double listings.

### Post-incident actions
- Blameless review within **48 hours** (owner: pod tech lead).
- Prove, with a query grouped by idempotency key, that **zero duplicate listings** were created.
- Confirm zone-redundant auto-failover is active.
- Add a **read replica** so reads survive a failover without relying only on stale cache.
- Add a "SQL slow (5 s/query)" game-day test; tune breaker thresholds if it opened too early or too late.

## Failure 2: Azure Cache for Redis is down

**In one line:** the cache is gone, so search reads the database directly — slower, but still working. This is the design behaving as intended (requirement N2).

### What the member sees
- Search **still returns books** — just slower, because every query now misses the cache and reads SQL.
- Normal browsing shows no errors. Login is unaffected, because tokens are checked without any cache.
- Risk: if the slowdown is bad enough, the **search-latency SLO (S1: 99% under 800 ms)** starts burning.

### Detection
Primary signal: Redis dependency failures in Application Insights.

```kusto
dependencies
| where timestamp > ago(5m)
| where type == "Redis"
| summarize failRate = round(100.0*countif(success==false)/count(),1) by bin(timestamp,1m)
// Alert: failRate > 10% for 2 minutes
```

Confirming signal: Azure Cache for Redis `Errors` rising, `Connected Clients` dropping, or `Cache Hits` falling toward zero while traffic stays steady.

### Mitigation in design
- **Timeout:** connect 1000 ms, operation 250 ms — a dead cache adds at most a quarter-second before we move on, not seconds.
- **Retry:** just **1** retry at 100 ms, then give up. The cache is not the source of truth, so aggressive retries would only slow every request.
- **Circuit breaker (Redis):** opens quickly and, while open, we **skip Redis entirely** and read SQL — so we don't pay the connect timeout on every request.
- **Fallback:** the cache-aside pattern means SQL is always the source of truth, so on a miss we simply read SQL. An optional in-process **LRU cache** (Least Recently Used — keeps the ~200 hottest queries in app memory for 10 s) can shield SQL further, with no new vendor.
- **Protect SQL:** the write-reserved connection pool (the bulkhead) stops the read flood from starving `POST /books`. Under pressure, **degrade search**: smaller page size, disable facets.

### Manual response
- **Who is paged:** primary on-call (Sev3, escalating to **Sev2** if the S1 SLO-burn alert also fires).
- **Steps:**
  1. Check **Azure Cache for Redis** resource health and metrics (server load, evictions, connected clients).
  2. Confirm the Redis breaker is **open** and traffic is failing over to SQL.
  3. Watch **SQL CPU / DTU** (Database Transaction Units — Azure's measure of database load). If SQL is saturating, turn on **degraded search** and tighten rate limits.
  4. Reboot or scale the Redis instance as needed.
  5. When Redis is back, confirm the cache **warms** and search latency returns under 800 ms.

### Post-incident actions
- Review (owner: pod tech lead).
- Run a **game day** that actually kills Redis under load, to prove the fail-open path holds — don't just trust the design.
- Add **cache pre-warm on deploy** so a cold cache after a release doesn't look like an outage.
- Move Redis to a **zone-redundant / clustered** tier.
- Add a combined alert: "Redis down **and** SQL CPU > 80%" — that pairing is the real danger.

## Failure 3: Sunday tabloid spike — 10× traffic for 4 hours

**In one line:** traffic jumps to 10× for four hours. We scale out ahead of time, rate-limit abusive callers, and lean on idempotency so the wave of retries never creates duplicates.

### What the member sees
- **If handled:** the app is a little slower but usable — new listings still go through, search still returns.
- **If unhandled:** `429` / `5xx` responses, "List my book" failing, search spinning. Members then retry, and without idempotency those retries would create **duplicate listings** — the exact trap this scenario tests.

### Detection
Early-warning signal: request rate climbing in Application Insights.

```kusto
requests
| where timestamp > ago(10m)
| summarize rps = count()/60.0 by bin(timestamp,1m)
// Alert: rps > 5× the 7-day baseline for 5 minutes (early warning)
```

Saturation signals: App Service `CpuPercentage` > 70% for 5 min, `HttpQueueLength` rising, `5xx` rate > 1%, and Service Bus `ActiveMessages` (the email-digest queue) backing up.

### Mitigation in design
- **Scheduled pre-scale (this is a *known* event):** the day before, raise App Service to **min 6 instances** for the busy window and **scale up the SQL tier** (or attach a read replica). Because the app is stateless, any instance can serve any request, so scaling out is safe.
- **Autoscale:** add instances at CPU > 65%, up to **max 10**; scale back afterwards.
- **Rate limiting (Front Door WAF):** **100 write requests / 60 s per IP** → `429` with `Retry-After: 30`; a global cap protects the backend.
- **Queue-based load levelling:** email digests already flow through **Service Bus**, so bursts are absorbed and workers drain at a steady pace.
- **Idempotency under retry storms:** timeouts make members retry more, so `POST /books` **requires the idempotency key** — repeated keys return the original `201`, so a surge of retries never creates duplicates (requirements N4, N11).
- **Graceful degradation:** feature-flag off expensive extras (facets, recommendations) during the window → this protects **search availability (S2)** even when the **latency SLO (S1) cannot be met** — the honest bet from the SLO map.

### Manual response
- **Who:** primary on-call **drives**; **pod tech lead** on standby; a **comms owner** watches the status page. This is half-planned, not a pure surprise.
- **Steps:**
  1. **Day before:** run the pre-scale checklist (min 6 instances, SQL tier up, degraded-mode flags ready).
  2. **During:** watch the dashboard — RPS, CPU, SQL DTU, `5xx`, queue depth.
  3. If CPU > 85% or `5xx` climbs → **add instances / raise the autoscale max**.
  4. If SQL saturates → **enable degraded search** and tighten write rate limits.
  5. After 4 hours → **scale back down**, re-enable features, post an "all clear".

### Post-incident actions
- Run a **success retro** even if it went fine (owner: pod tech lead).
- Record the **actual peak RPS** versus the assumed 10× and **right-size autoscale** from real data.
- Query for would-be duplicate creates grouped by idempotency key, to **prove** the dedupe worked.
- Decide whether **scheduled pre-scaling** should be automated for future features.
- Feed the result back into the SLO map's **"out of budget right now"** item.

## Quick reference: how each failure is detected

| Failure | Main signal (queryable) | Alert threshold | Pages within |
|---|---|---|---|
| SQL primary down | SQL dependency failure rate | > 25% for 2 min | ~3 min |
| Redis down | Redis dependency failure rate | > 10% for 2 min | ~3 min |
| 10× spike | Request rate + App Service CPU | RPS > 5× baseline, or CPU > 70% for 5 min | ~5 min (early warning) |
