# BookSwap — SLI/SLO Map

This document takes each quality promise from the Day 2 design and turns it into two things: a number we can **measure**, and a **target** we commit to.

Context for the numbers below: BookSwap now runs across **200 buildings** (up from 1), and a Sunday newspaper feature is expected to push traffic to about **10× normal for ~4 hours**. The code does not change today — this document proves the design is ready, or names what would have to change.

### Key terms (used throughout)

- **NFR (Non-Functional Requirement)** — a quality promise like *fast*, *safe*, *reliable*. Not a feature.
- **SLI (Service Level Indicator)** — the number we actually measure (e.g. "% of searches under 800 ms").
- **SLO (Service Level Objective)** — the target we commit to, always with a time window (e.g. "99% over 28 days").
- **Error budget** — how much failure the SLO still allows. It is simply `100% − SLO`.
- **RPS (Requests Per Second)** — how busy the service is.

The chain to keep in mind: **NFR → SLI → SLO → error budget.** A promise becomes a number, the number gets a target, and the target leaves room for a little failure.

## 0. Assumptions about the Day 2 API

SLOs attach to endpoints, so first, here are the endpoints I assumed from the Day 2 design. If your `bookswap-openapi.yaml` uses different names, only the labels below change — the logic stays the same.

| Assumed endpoint | Purpose |
|---|---|
| `GET /books` | Catalogue **search** / list |
| `GET /books/{bookId}` | Single book detail |
| `POST /books` | **Create a listing** |
| `POST /loans` | Borrow a book (create loan) |
| `POST /loans/{loanId}/return` | Return a book |
| `GET /members/{memberId}/loans` | A member's **loan history** |
| `GET /members/{memberId}` | Member profile (**contains address**) |
| `GET /health` | Health check — the **only** endpoint that needs no login |

Throughout, "listings endpoint" means `POST /books` and `GET /books` together.

## 1. NFR inventory

First, every Day 2 promise, restated as something a member would actually notice. This includes a few requirements written as features that are really quality promises in disguise (for example, "search stays useful when the cache is cold" is really a *resilience* promise).

| # | Requirement | What a member notices |
|---|---|---|
| N1 | Search: 99% of requests under 800 ms over 28 days, even at 10× RPS | Typing a title returns results fast, even on a busy Sunday. |
| N2 | Search stays useful when the cache is cold or down | Right after a deploy, or if the cache fails, search still returns books — maybe a touch slower, never broken. |
| N3 | Listing creation: 99.9% success | Tapping "List my book" almost always works and the book appears. |
| N4 | Failed listings retryable **without duplicates** | If I double-tap or my phone retries, I get **one** listing, not two. |
| N5 | Every endpoint except `/health` needs a valid login token | I can only use the app when signed in. |
| N6 | Tokens expire within 1 hour | A stolen or stale token stops working within an hour. |
| N7 | A member never sees another member's loans or address | I see **my** loans and address, never my neighbour's. |
| N8 | A full outage of the listings endpoint pages on-call within 3 minutes | If listings break at 2 a.m., a human is woken fast, so outages stay short. |
| N9 | Every login failure and every borrow/return is logged with request ID + member ID | Every failed login and every loan is traceable. |
| N10 | Operations can confirm health in under 5 minutes | On-call can say "healthy / not healthy" quickly, from one dashboard. |
| N11 | Keep accepting new listings during the 10× / 4-hour spike | New listings keep going through during the surge. |

## 2. SLI / SLO table

Next, each promise becomes a measurable target. The requirements split into **two groups**, and telling them apart is the most important idea on this page:

- **Group A — statistical targets.** Some failure is acceptable (and even useful, because it lets us ship). These get an SLO **and an error budget**.
- **Group B — hard invariants.** Things like privacy and login must simply always hold. The acceptable failure rate is **zero**, so they get **no budget**. A breach is a bug, not "spending the budget."

> Error budgets are shown as a percentage **and** an illustrative count. Counts assume **~2,000,000 searches** and **~200,000 listing creates** per 28 days — swap in real traffic when you have it.

### Group A — statistical SLOs (with error budgets)

| # | What we measure (SLI) | Where it comes from | Target (SLO) | Window | Error budget |
|---|---|---|---|---|---|
| S1 | **Search latency** — % of `GET /books` returning success in **under 800 ms** | Application Insights `requests` | **≥ 99%** | 28 days | 1% (~20,000 slow searches) |
| S2 | **Search availability** — % of `GET /books` returning non-error (protects N2) | Application Insights `requests` | **≥ 99.5%** | 28 days | 0.5% (~10,000 failed searches) |
| S3 | **Listing-create success** — % of `POST /books` succeeding, ignoring bad-input errors | Application Insights `requests` | **≥ 99.9%** | 28 days | 0.1% (~200 failed creates) |
| S4 | **Spike write availability** — % of `POST /books` succeeding **during the 10× window** (relaxed on purpose) | Application Insights `requests`, spike window only | **≥ 99%** | Per spike | 1% of spike creates |
| S5 | **Detection speed** — % of listings outages where the page fires **within 3 minutes** | Alert-fired time − first-failure time | **≥ 99%** | 90 days | 1% may page late |
| S6 | **Audit completeness** — % of login-fail + loan events logged with request ID **and** member ID | Application Insights `traces` | **≥ 99.9%** | 28 days | 0.1% may miss a field |
| S7 | **Ops confidence** — % of practice drills where on-call declares health **within 5 minutes** | Drill stopwatch + dashboard freshness | **≥ 95%** | Per quarter | 5% of drills may run long |

### Group B — hard invariants (target is exactly 100%, no budget)

| # | What we check | Where it comes from | Target | If broken |
|---|---|---|---|---|
| I1 | **Login is enforced (N5)** — protected endpoints reject requests with no valid token | `requests` where the URL is not `/health` and the result is 401/403 | **100%** | Security incident |
| I2 | **Token lifetime (N6)** — no access token lives longer than 1 hour | Entra External ID token policy + a synthetic check | **100%** | Config fix + rotate |
| I3 | **Privacy / BOLA (N7)** — no member ever reads another member's data. BOLA = **Broken Object Level Authorization** | Security tests + audit-log anomalies | **0 incidents** | Privacy incident |
| I4 | **No duplicate listings (N4)** — a retried create stores exactly one row | Idempotency-key store + database uniqueness stats | **100%** | Data-correctness bug |

### Sample queries (so any engineer can reproduce the number)

These are written in **KQL (Kusto Query Language)**, the query language for Application Insights. Each one is the exact query behind an SLI above.

Search latency (S1) — the share of searches that were both successful and under 800 ms:

```kusto
requests
| where timestamp > ago(28d)
| where name == "GET /books"
| summarize good = countif(success == true and duration < 800),
            total = count()
| extend sli_pct = round(100.0 * good / total, 3)
```

Listing-create success (S3) — we ignore 4xx (client mistakes) so we only measure **our** failures. HTTP status codes: 2xx = success, 4xx = caller error, 5xx = server error.

```kusto
requests
| where timestamp > ago(28d)
| where name == "POST /books"
| where toint(resultCode) < 400 or toint(resultCode) >= 500   // ignore 4xx
| summarize good = countif(toint(resultCode) < 400),
            total = count()
| extend sli_pct = round(100.0 * good / total, 3)
```

Audit completeness (S6) — events that carry **both** required fields:

```kusto
traces
| where timestamp > ago(28d)
| where customDimensions.event in ("auth.failed","loan.created","loan.returned")
| summarize good = countif(isnotempty(customDimensions.requestId)
                       and isnotempty(customDimensions.memberId)),
            total = count()
| extend sli_pct = round(100.0 * good / total, 3)
```

Login-enforcement leak detector (I1) — flags any protected endpoint that returned success with no signed-in member:

```kusto
requests
| where timestamp > ago(1d)
| where url !endswith "/health"
| where toint(resultCode) < 300
| where isempty(customDimensions.memberId)   // success but nobody logged in = leak
| project timestamp, name, url, resultCode
```

## 3. Error budget policy

An error budget is only real if running out of it *changes behaviour*. Here is what changes.

**When a Group A budget runs out early** (for example, the 1% search-latency budget is spent before the 28-day window ends):

- The team **freezes new features** on that service. Only three kinds of change may ship: rollbacks, reliability fixes, and urgent bug fixes.
- The freeze lifts only after the number is back inside budget and **stays green for 7 days**.

**When a Group B invariant is broken** (login, privacy, or duplicates): there is no budget to argue over. It becomes an incident immediately, and the same feature freeze applies until it is fixed.

**Who decides:** the **BookSwap pod tech lead** (the service owner) calls the freeze. Disputes go to the **Engineering Manager**. On-call *raises* the flag but does not decide alone. *(Fill in real names before submission.)*

## 4. Out of budget right now

One honest sentence: which target would I bet we **cannot** meet today?

> **Search latency (S1: 99% under 800 ms) during the Sunday spike, if the cache is cold or down.**

Why: with no cache, every search falls straight through to the database. At 10× RPS against a database tier sized for a single building, queries will queue and blow past 800 ms. Since the code does not change today, the truthful position is: **steady-state, yes; spike-with-cold-cache, no.**

What would have to change (named here, fixed in the reliability runbook): a **read replica or bigger database tier** for the spike, **cache pre-warming** on deploy, and a **degraded-search fallback** so availability (S2) survives even when latency (S1) cannot.
